# Cairn v0.2.0 — Access & Sharing Design

**Status:** Approved (brainstorming complete)
**Date:** 2026-05-21
**Target release:** v0.2.0
**Builds on:** v0.1.0 (see `2026-05-20-cairn-design.md`)

## 1. Purpose

v0.2.0 expands *who* can get into a Cairn instance and *what* they can reach, without adding new infrastructure services. Three features:

1. **OAuth login** (Google + GitHub) as an alternate front door that respects the existing invite gate.
2. **Multi-workspace switching** — a user can belong to and move between multiple workspaces on one instance.
3. **Public read-only sharing** — anonymous, link-only published pages.

Guiding constraint: the instance stays **invite-gated** (no open self-registration). OAuth and multi-workspace creation are conveniences for already-admitted, trusted users, not a path for strangers to get in.

## 2. Scope

### In scope

- OAuth providers Google + GitHub, conditionally enabled per env, invite-gated, linked by verified email.
- Multi-workspace: active-workspace resolution in `getAuthContext`, sidebar switcher, workspace creation, switch, invite-accept for existing logged-in users, leave-workspace.
- Public sharing: publish/unpublish toggle, anonymous `/p/<slug>` read-only render (including read-only embedded databases), `noindex`, single-page scope.
- Migration `0007`: `users.email_verified`, `users.image`, `pages.published`, `pages.public_slug`.

### Explicitly deferred

- Owner-transfer and workspace deletion → v0.2.x follow-up.
- Block-level permissions → v0.3.x+.
- Real-time collaboration, comments/@mentions, notifications → v0.3.0.
- Sharing variants not chosen: authenticated-only shares, password-protected links, subtree publishing, public search-indexing opt-in, custom domains.
- OAuth providers beyond Google/GitHub (trivial to add later via Auth.js config).

### Operational note

This release introduces Cairn's **first unauthenticated content paths** (`/p/**`, `/api/public/**`). Security rests on three independent checks:
- Only pages with `published = true AND deleted_at IS NULL` resolve at `/p/<slug>`.
- Embedded-database reads on a public page authorize via the containing page's `published` flag, not a session.
- Embedded images/files remain served only through HMAC-signature-gated `/api/files/[id]` URLs (re-minted server-side at public-render time).

## 3. Data model

Single migration `0007_access_and_sharing.sql`.

### 3.1 Users (OAuth)

```
users
  + email_verified  timestamptz null   -- set from the OAuth provider; null for credentials-only users
  + image           text null          -- avatar URL from the provider
```

These two columns are what the `@auth/drizzle-adapter` expects on the users table. Adding them lets us **remove the `AdapterTableMap = any` cast** in `src/lib/auth/config.ts` (v0.1.0 workaround). The existing `accounts` table (present but inert under credentials/jwt) becomes **live**: Auth.js persists OAuth identities and links them to users there.

### 3.2 Pages (sharing)

```
pages
  + published    boolean not null default false
  + public_slug  text unique null   -- minted on first publish; stable across re-publishes; retained when unpublished
```

`public_slug` format: `<slugified-title>-<6 hex chars>` (e.g. `roadmap-7f3a9c`). The random suffix avoids collisions and guessing. A page keeps its slug forever once minted, so re-publishing reuses the same URL.

### 3.3 Active workspace (multi-workspace)

No schema change. The active workspace is held in an **httpOnly cookie `cairn_ws`** (workspace UUID), validated against `workspace_members` on every `getAuthContext()`. Rationale: jwt sessions would require re-issuing the token on each switch; "which workspace am I viewing" is a per-session UI preference, not durable user data; and `getAuthContext` already queries memberships so validating the cookie is nearly free.

`workspace_members` (composite PK on workspace+user, from v0.1.0) already models a user in many workspaces — multi-workspace is largely *activating* this, not a schema change.

## 4. OAuth

### 4.1 Provider configuration

- Google and GitHub providers are added to the Auth.js config **only when their env vars are present**: `AUTH_GOOGLE_ID` / `AUTH_GOOGLE_SECRET`, `AUTH_GITHUB_ID` / `AUTH_GITHUB_SECRET`. An instance that configures neither shows only the existing credentials login — no dead buttons.
- The login and signup pages query `GET /api/auth/providers` (Auth.js built-in) to render "Continue with Google/GitHub" buttons only for enabled providers.
- The credentials provider is unchanged.

### 4.2 Invite-gated sign-in flow

A `signIn` callback (in `src/lib/auth/config.ts`) enforces the gate for OAuth sign-ins. Decision tree, keyed on the provider's verified email:

1. **A user with that email already exists** → link the OAuth identity (`accounts` row) to that user and allow. (An invited user who first signed up with a password can later "Continue with Google" on the same email and it just works.)
2. **No user, but a valid unused invite token for that email exists** → create the user, consume the invite (set `used_at`), insert the `workspace_members` row with the invited role, allow.
3. **Neither** → reject; redirect to a "you need an invite" page. No silent workspace creation via OAuth.

`email_verified` is populated from the provider, so steps 1–2 are safe against email spoofing (Google/GitHub assert verified emails).

### 4.3 Implementation note (resolved in plan, not spec)

Auth.js's Drizzle adapter may auto-create the user around the `signIn` callback for OAuth. The plan determines the exact mechanism (e.g. handling creation+gating inside `signIn` and/or `events.createUser` / `events.linkAccount`, or `allowDangerousEmailAccountLinking` with our own guard). The design commitment is fixed: **OAuth obeys the invite gate; account linking is by verified email.**

## 5. Multi-workspace switching

### 5.1 getAuthContext (central change)

```
getAuthContext():
  session = auth()
  if no session.user.id → null
  memberships = all workspace_members for the user
  if memberships empty → return a "no workspace" context (userId only, workspaceId null)
  active = cookie cairn_ws, if it names one of the memberships → that one
           else → oldest membership (and set the cookie)
  return { userId, workspaceId: active.workspaceId, role: active.role }
```

Roles are per-workspace: the returned `role` is the role held in the *active* workspace. Every existing route's scoping flows through this unchanged.

The "no workspace" context (a logged-in user belonging to zero workspaces) is reachable after leaving the last workspace or via an invite-less OAuth edge. The `(app)` layout renders a **"no workspace" empty state** (offer to create a workspace or note that an invite is required) instead of redirecting to login.

### 5.2 Endpoints

- `POST /api/workspaces` — any authenticated user creates a workspace; becomes its `owner`; the new workspace is set active (cookie). Generalizes the v0.1.0 bootstrap into a reusable `createWorkspace(name, ownerUserId)` helper used by both bootstrap and this route.
- `POST /api/workspaces/switch` — body `{ workspaceId }`; validates the caller is a member; sets the `cairn_ws` cookie; returns ok. Client revalidates.
- `POST /api/workspaces/[id]/leave` — removes the caller's own membership. **Rejected if the caller is the workspace's only `owner`** (no transfer/delete in 0.2.0). On success, switches active workspace to another membership, or to the "no workspace" state if none remain.
- `POST /api/invites/accept` — body `{ token }`; for the current authenticated user, validates the invite token, requires the invite's email to equal the user's verified email, adds the membership with the invited role, marks the token used, and switches active workspace to it.

### 5.3 UI

- **Workspace switcher**: a dropdown at the top of the sidebar showing the active workspace name; lists the user's other workspaces (switch on click), plus "Create workspace" and the existing admin/owner invite action.
- **Invite landing page** `/invite/[token]`:
  - Logged out → bounce to `/signup` with the token (existing signup-with-invite flow).
  - Logged in → "Accept invite to join <workspace>" button calling `POST /api/invites/accept`.
- **No-workspace empty state** in the `(app)` area (see 5.1).

## 6. Public sharing

### 6.1 Publish control

The page overflow menu (`PageMenu`) gains **Publish to web / Unpublish**. When published, it shows the public URL (`/p/<slug>`) with a copy button.

- `POST /api/pages/[pageId]/publish` (editor+) — sets `published = true`, mints `public_slug` if absent, returns the slug/URL.
- `POST /api/pages/[pageId]/unpublish` (editor+) — sets `published = false`, retains the slug.

### 6.2 Public render route `/p/[slug]`

Outside the `(app)` route group; no auth, no sidebar.
- Server component looks up the page by `public_slug WHERE published = true AND deleted_at IS NULL`; `notFound()` otherwise.
- Renders read-only via **TipTap with `editable: false`** reusing the existing extension set (callouts, code highlight, lists, etc. render identically — no second renderer to maintain). No autosave, no slash menu, no drag handle on this surface.
- **Images/files:** the server walks the document and re-mints a fresh HMAC-signed URL from each `cairnImage`/`fileAttachment` node's stored `fileId` at render time, so anonymous visitors get valid (1-hour) URLs that never go stale across renders. `/api/files/[id]` validates only the signature (no session), so anonymous fetch already works.
- **Embedded databases** render read-only via `GET /api/public/databases/[databaseId]` (see 6.3).
- **Scope guard:** only the published page renders. Child-page links embedded in the content are inert (not navigable) on the public surface, since descendants are not published.
- Emits `<meta name="robots" content="noindex">` — unlisted, link-only.

### 6.3 Public database read path

- `GET /api/public/databases/[databaseId]` — returns the database meta + rows **read-only**, authorized by confirming the database's containing `page.published = true`. No session required, no write operations exposed under `/api/public`.
- Filters/sorts come from the database's default/embedded view config, same as the authenticated read path.

### 6.4 Middleware

Add `/p/**` and `/api/public/**` to the middleware public-path allowlist. (`/api/files/**` is already signature-gated and public.) `/api/auth` and `/api/health` remain public as before.

## 7. Security considerations

- **Unauthenticated surface:** `/p/<slug>` and `/api/public/databases/[id]` are the only new anonymous content paths. Both gate strictly on `published = true`; the database read additionally joins to its page to confirm publication. There is no anonymous write path.
- **Email-based account linking** is only trusted because `email_verified` is asserted by the OAuth provider; credentials-only users have `email_verified = null` and are matched by the existing unique-email constraint.
- **Cross-workspace isolation** is unchanged and still enforced by `getAuthContext` + per-route workspace scoping; multi-workspace just changes *which* workspace is active, never bypasses scoping.
- **Slug guessing:** the 6-hex-char random suffix on `public_slug` makes published URLs effectively unguessable while staying human-readable; combined with `noindex`, published pages are unlisted.
- **Cookie validation:** `cairn_ws` is httpOnly and always re-validated against live membership; a stale or forged value falls back to the oldest membership rather than granting access.

## 8. Testing strategy

- **Unit/integration (Vitest + Testcontainers):**
  - `getAuthContext` active-workspace resolution: valid cookie, invalid/forged cookie → fallback, no-membership → null context.
  - `createWorkspace`, switch, leave (incl. sole-owner rejection), invite-accept (email match required, token consumed, membership added).
  - OAuth `signIn` gate logic: existing-user link, valid-invite create, rejection — exercised at the helper/callback level (the real OAuth handshake is mocked, consistent with v0.1.0's `vi.mock('@/lib/auth/config')` pattern).
  - publish/unpublish; public page lookup (published vs unpublished vs deleted vs wrong slug); public database read authorized by page publication.
- **E2E smoke (docker compose + curl):** OAuth provider list reflects configured env; create a second workspace + switch; accept an invite as an existing user; publish a page and fetch `/p/<slug>` anonymously (no cookie) including an embedded image and a read-only database; unpublish → `/p/<slug>` 404s.

## 9. Plan decomposition

Likely four plans, executed in order, each producing testable software:

1. **OAuth & user-model** — migration `0007` carrying **all four columns** (`users.email_verified`, `users.image`, `pages.published`, `pages.public_slug`) so the schema lands coherently in one step; conditional Google/GitHub providers; invite-gated `signIn` callback; login/signup provider buttons; drop the adapter `any` cast. (The `pages` columns are added here but not consumed until plan 3.)
2. **Multi-workspace** — `getAuthContext` active-workspace + cookie, `createWorkspace` generalization, workspaces/switch/leave/invite-accept endpoints, switcher UI, invite landing page, no-workspace empty state.
3. **Public sharing** — publish/unpublish endpoints + menu (consuming the `pages.published`/`public_slug` columns from plan 1's migration), `/p/[slug]` read-only render with image re-signing, `/api/public/databases/[id]`, middleware allowlist, noindex.
4. **Polish & release** — e2e smoke across all three, README/CHANGELOG, `.env.example` additions (OAuth vars), tag `v0.2.0`.
