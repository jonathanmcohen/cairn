# Cairn v0.3.0 — Real-time Collaboration Design

**Status:** Draft (autonomously specced from the roadmap at the user's direction — design decisions made on their behalf and flagged below; not interactively brainstormed). Subject to revision before implementation.
**Date:** 2026-05-21
**Target release:** v0.3.0
**Builds on:** v0.2.0 (access & sharing)

## 1. Purpose

Make Cairn multiplayer: multiple people editing the same page live, seeing each other's cursors, leaving comments, getting mentioned, and being notified. This is the largest infrastructure change in the 0.x line — it breaks v0.1.0's "single process, no horizontal scaling" non-goal by introducing a stateful WebSocket layer.

## 2. Key decisions (made autonomously; revisit before building)

1. **WebSocket topology — a dedicated collab service.** Real-time editing needs a long-lived stateful WebSocket server, which the Next.js standalone server isn't suited to host. We add a **second container in docker-compose, `cairn-collab`, running [Hocuspocus](https://tiptap.dev/hocuspocus)** (the TipTap-blessed Yjs backend). It shares the same Postgres for persistence. Rationale: clean separation (Next stays stateless/horizontally-scalable; collab state lives in one place), official TipTap integration, and it sidesteps re-architecting the Next entrypoint. Tradeoff: the deployment is no longer single-container. *Alternative considered:* running Hocuspocus as a second process inside the Next container — rejected as harder to supervise/scale and muddier than a compose service.
2. **Doc storage model.** Yjs becomes the live edit state. Hocuspocus persists each page's Yjs document (binary) to a new `page_yjs` table via its database extension. On debounced change and on last-client-disconnect, the collab server materializes the Yjs doc back into `pages.content` (ProseMirror JSON) + lets the existing trigger refresh `content_text`/`content_tsv`. So **search, export, and public render keep reading `pages.content`** unchanged — Yjs is additive.
3. **Collab auth.** The Next app mints a short-lived collab JWT (signed with `AUTH_SECRET`, claims: userId, pageId, role, exp) which the client passes on WS connect. Hocuspocus `onAuthenticate` verifies the JWT and the page-level permission (mirrors `requirePageAccess`). No unauthenticated editing; public pages remain read-only and are NOT served over the collab socket.
4. **Notifications delivery.** Simple polled feed (`GET /api/notifications`) + unread badge, not a push channel, for v0.3.0. Avoids coupling notifications to the collab socket. Push can come later.
5. **Autosave replacement.** The v0.1.0 debounced PATCH autosave is superseded for collaborative pages by Yjs sync; the materialize-to-`content` step replaces the explicit save. The conflict-detection logic becomes unnecessary for collab edits (Yjs is conflict-free) and is retired on that path.

## 3. Scope

### In scope
- Yjs collaborative editing on pages via Hocuspocus + `y-prosemirror`, with the `cairn-collab` compose service and Postgres persistence.
- Live presence: remote cursors, selections, and avatars (Yjs awareness).
- Comments: block/range-anchored threads, resolve/reopen, per-page.
- @mentions: autocomplete over workspace members, mention nodes, links to the mentioned user.
- Notifications: a `notifications` table, polled feed + unread badge, triggered by mentions and comment replies.
- Migration `0008` (page_yjs, comments, comment-related, notifications).

### Deferred
- Push notifications / email notifications → later.
- Comment threads on databases or files → pages only for now.
- Presence in the public/read-only view → no (public is anonymous, no presence).
- Horizontal scaling of the collab service (multiple Hocuspocus replicas + Redis pub/sub) → single collab instance for homelab; document the ceiling.
- Offline editing / merge on reconnect beyond what Yjs gives for free.

## 4. Data model (migration `0008`)

```
page_yjs
  page_id     uuid pk references pages(id) on delete cascade
  state       bytea not null            -- Yjs document binary (Hocuspocus-managed)
  updated_at  timestamptz not null default now()

comments
  id           uuid pk
  workspace_id uuid not null references workspaces(id) on delete cascade
  page_id      uuid not null references pages(id) on delete cascade
  author_id    uuid not null references users(id) on delete restrict
  body         text not null
  anchor       jsonb null                -- { blockId } or { from, to } range; null = page-level
  resolved_at  timestamptz null
  created_at   timestamptz not null default now()
  updated_at   timestamptz not null default now()

notifications
  id           uuid pk
  user_id      uuid not null references users(id) on delete cascade
  workspace_id uuid not null references workspaces(id) on delete cascade
  type         text not null             -- 'mention' | 'comment_reply'
  payload      jsonb not null            -- { pageId, commentId, actorId, ... }
  read_at      timestamptz null
  created_at   timestamptz not null default now()
```

Mentions are parsed from comment/body content (`@<userId>` tokens) rather than a join table for v0.3.0 simplicity; a mention creates a `notifications` row of type `mention`.

## 5. Architecture by area

- **`cairn-collab` service:** a small Node app (its own `Dockerfile.collab` or a build target) running Hocuspocus with the Postgres persistence extension + an `onAuthenticate` hook verifying the collab JWT. Exposed on a WS port; docker-compose wires it next to `cairn` + `db`. The Next app gets a `COLLAB_URL` env for the browser to connect.
- **Editor integration:** the TipTap editor swaps its single-doc model for `Collaboration` + `CollaborationCursor` extensions bound to a `Y.Doc` synced via `HocuspocusProvider`. The editor fetches a collab token from a new `GET /api/collab/token?pageId=` (Next route, `requirePageAccess('editor')` → mints JWT). Read-only viewers connect with a viewer-role token (no awareness write).
- **Materialization:** the collab server, on debounce/disconnect, converts the Yjs doc → ProseMirror JSON and writes `pages.content` (via a direct DB update or a callback to a Next internal endpoint). Decide in the plan: simplest is the collab server writing `pages.content` directly using the same `pages_sync_search_columns` trigger to refresh FTS.
- **Comments:** `src/lib/comments/*` helpers + `/api/pages/[id]/comments` routes; an editor-margin comment UI keyed to anchors; resolve/reopen.
- **Mentions:** a TipTap mention extension (suggestion-based, like the slash menu) querying `/api/workspaces/members?q=`; mention nodes store userId; rendering links to the user.
- **Notifications:** `src/lib/notifications/*`, `GET /api/notifications` (+ mark-read), a bell component polling every ~30s.

## 6. Security
- Collab JWTs are short-lived (e.g. 5 min), page- and role-scoped; the collab server re-checks on connect. A revoked/expired token drops the connection.
- The collab service shares Postgres credentials; it must NOT expose any HTTP surface beyond the WS endpoint.
- Comments/notifications are workspace-scoped exactly like pages; the public render path never loads comments or the collab socket.

## 7. Plan decomposition (~6 plans)

1. **Collab infrastructure** — `0008` migration (`page_yjs`), `cairn-collab` Hocuspocus service + Dockerfile + compose wiring, collab JWT mint/verify (`/api/collab/token` + shared verify lib), `onAuthenticate`. Verifiable by a WS connect smoke.
2. **Collaborative editing** — `Collaboration`/`CollaborationCursor` in the editor, `HocuspocusProvider` wiring, retire the PATCH-autosave on the collab path, materialize Yjs→`pages.content`. 
3. **Presence** — awareness cursors/labels/avatars, presence-aware UI.
4. **Comments** — schema (folded into `0008` or `0009`), helpers, API, anchored comment UI, resolve/reopen.
5. **@mentions** — mention extension + member-search API + mention nodes + linking; mention → notification trigger.
6. **Notifications + release** — notifications schema/helpers/feed/bell, wire mention + comment-reply triggers, e2e, README/CHANGELOG, tag `v0.3.0`.

## 8. Risks
- Hocuspocus + `y-prosemirror` + our custom node extensions (callout, image, file, database) must all be Yjs-serializable; the database node (atom referencing a `databaseId`) is fine, but verify each during plan 2.
- Materialization timing (debounce vs disconnect) must not lose the last edits; test the disconnect path explicitly.
- The collab service is a new operational surface (a second image to build/publish in the release workflow) — plan 6/release accounts for building+publishing `cairn-collab` too.
