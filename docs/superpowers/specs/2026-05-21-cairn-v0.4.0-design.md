# Cairn v0.4.0 — Database Depth Design

**Status:** Draft (autonomously specced from the roadmap at the user's direction; design decisions made on their behalf and flagged below; not interactively brainstormed). Subject to revision before implementation.
**Date:** 2026-05-21
**Target release:** v0.4.0
**Builds on:** v0.3.0

## 1. Purpose

Bring Cairn's inline databases (built in v0.1.0 Plan 5) toward Notion parity: computed **formula** properties, **relations** linking rows across databases, **rollups** aggregating related rows, and **calendar** + **timeline** views. This release is self-contained within the database subsystem — no new infrastructure.

## 2. Key decisions (made autonomously; revisit before building)

1. **Formulas evaluate at read time, in JS.** A `formula` property stores its expression in `config`; its value is computed per row when rows are read (in `listRows` / the row API), never persisted. Rationale: always-fresh, no recompute-on-dependency-change bookkeeping, no stored staleness. Tradeoff: can't filter/sort on a formula in SQL (computed after the SQL fetch) — for v0.4.0, filtering/sorting on formula properties is **not supported** (documented limitation); they display only.
2. **A small, safe expression language — not arbitrary JS.** Implement a tiny parser/evaluator (or wrap a vetted micro-lib like `expr-eval`) supporting: number/string/boolean literals, property references by name, arithmetic (`+ - * / %`), comparisons, `if(cond, a, b)`, `concat(...)`, `length()`, basic math (`round`, `abs`, `min`, `max`, `sum` over args), and a few date helpers (`now()`, `dateDiff(a, b, unit)`). No I/O, no loops, no host access. Unknown functions/refs → the cell shows an error marker, not a crash.
3. **Relations store row-id arrays; integrity is read-time-filtered.** A `relation` property's `config` holds `{ targetDatabaseId }`; a cell value is `string[]` of related `db_rows` ids. Deleting a related row does NOT eagerly rewrite every relation cell; instead reads filter out ids that no longer resolve (and a lightweight cleanup can compact them later). Reverse/bidirectional relations are **optional and deferred** within v0.4.0 (single-direction first; note the follow-up).
4. **Rollups depend on relations and also evaluate at read time.** A `rollup` property's `config` holds `{ relationPropertyId, targetPropertyId, fn }` with `fn ∈ count | sum | avg | min | max | earliest | latest`. At read time it follows the relation to the related rows, reads their `targetProperty` cell, and aggregates. Same no-filter/sort limitation as formulas.
5. **Calendar + timeline are new view types.** Add `'calendar'` and `'timeline'` to the `view_type` enum (migration). Calendar: a month grid placing rows on a chosen `date` property. Timeline: a horizontal time axis placing rows by a date (or a start/end date pair) property. Both reuse the existing view config (filters/sorts) and the read path; they're primarily UI.

## 3. Scope

### In scope
- `formula` property type + expression evaluator + read-time computation + property-panel formula editor + computed-cell display.
- `relation` property type + row-picker cell editor + read-time resolution + dangling-id filtering.
- `rollup` property type + read-time aggregation through a relation + config UI.
- `calendar` + `timeline` view types (enum migration) + their view UIs + view-switcher entries.
- Migration `0011` (extend `property_type` enum with `formula`/`relation`/`rollup`; extend `view_type` enum with `calendar`/`timeline`).

### Deferred
- Filtering/sorting ON formula/rollup values (they're computed post-SQL) → later.
- Bidirectional/reverse relations (auto reverse property) → v0.4.x follow-up.
- Cross-workspace relations → not allowed (relations only target databases in the same workspace).
- Formula functions beyond the documented set; rich date arithmetic → later.
- Relation/rollup recomputation caching → not needed (read-time).

## 4. Data model (migration `0011`)

No new tables. Extend two enums (Postgres `ALTER TYPE ... ADD VALUE`, which must run outside a transaction block — the migration notes this):

```
property_type: + 'formula', + 'relation', + 'rollup'
view_type:     + 'calendar', + 'timeline'
```

Property `config` jsonb carries the per-type settings (no schema change — `db_properties.config` already exists):
- formula: `{ expression: string }`
- relation: `{ targetDatabaseId: string }`
- rollup: `{ relationPropertyId, targetPropertyId, fn }`

Relation cell values: `string[]` (related row ids), coerced/validated on write (each id must be a live `db_rows` row in the target database).

## 5. Architecture by area

- **Formula engine:** `src/lib/databases/formula/` — `parse.ts` (tokenize + parse to AST), `evaluate.ts` (eval AST against a row's resolved cell values + property name map), `functions.ts` (the allowed function table). Pure + heavily unit-tested. `listRows` gains a post-fetch pass: for each `formula` property, evaluate against the row's cells; attach to the returned `cells` map under the property id. Errors surface as `{ __error: string }` cell values.
- **Relations:** extend `coerce` (in `src/lib/databases/rows.ts`) for `relation` (validate ids exist in the target db). A relation cell editor (`relation-cell.tsx`) opens a row picker querying the target database's rows. Read-time: `listRows` resolves relation cells to display labels (the related rows' title/first-text property), filtering dangling ids.
- **Rollups:** another `listRows` post-fetch pass: for each `rollup` property, follow its `relationPropertyId` cell → related row ids → fetch their `targetPropertyId` cells → aggregate by `fn`. Pure aggregation unit-tested; the fetch is batched.
- **Calendar view:** `calendar-view.tsx` — month grid; rows grouped by their date-property day; click a day to add a row prefilled with that date.
- **Timeline view:** `timeline-view.tsx` — horizontal lanes by date (or start/end), simple CSS positioning; v0.4.0 keeps it read-focused (drag-to-reschedule deferred).
- **Property panel:** add formula-expression input (with a live error hint), relation target-database picker, rollup config (relation property + target property + fn selectors). Add calendar/timeline to the view-switcher's add menu (each needs a date property chosen, like kanban needs a select property).

## 6. Testing strategy

- **Unit (Vitest):** formula parser + evaluator (literals, refs, arithmetic, comparisons, `if`, functions, error cases), rollup aggregation functions (count/sum/avg/min/max/earliest/latest, empty sets), relation id validation/coercion.
- **Integration (Testcontainers):** `listRows` returns computed formula + rollup values; relation cell write validates target-db membership; dangling relation ids filtered on read; property CRUD accepts the new types with their config schemas; view CRUD accepts calendar/timeline (calendar/timeline require a date property in config, validated like kanban's groupBy).
- **Build-verified:** the calendar/timeline view UIs, the property-panel additions, the relation row-picker.

## 7. Plan decomposition (~5 plans)

1. **Formulas** — `0011` migration (enum extensions), formula parser/evaluator/functions, `listRows` formula pass, property-panel formula editor + computed-cell display.
2. **Relations** — relation property type + config schema, `coerce`/validation, relation cell write API, row-picker editor, read-time resolution + dangling filtering.
3. **Rollups** — rollup property type + config schema, `listRows` rollup pass (depends on relations), rollup config UI.
4. **Calendar + timeline views** — view-type enum already extended in `0011`; calendar + timeline view components, date-property selection, view-switcher entries.
5. **Polish & release** — cross-feature e2e (a database with formula + relation + rollup + a calendar view), README/CHANGELOG, version bump, human-run `v0.4.0` tag.

## 8. Risks
- The expression language is the main effort/risk; keep the function set small and the evaluator pure + exhaustively tested. Prefer wrapping a vetted micro-lib if it cleanly supports the needed surface and is safe (no host access).
- Read-time formula/rollup passes add per-row computation; batch relation/target fetches to avoid N+1. Document the no-filter/sort-on-computed limitation prominently in the UI.
- `ALTER TYPE ADD VALUE` cannot run inside a transaction in older PG, and added enum values can't be used in the same transaction — the migration must account for this (separate statements / `--> statement-breakpoint`, and the new values are usable in subsequent migrations/queries).
