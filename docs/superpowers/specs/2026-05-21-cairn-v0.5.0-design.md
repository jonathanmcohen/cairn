# Cairn v0.5.0 — Platform & Operations Design

**Status:** Draft (autonomously specced from the roadmap at the user's direction; design decisions made on their behalf and flagged below; not interactively brainstormed). Subject to revision before implementation.
**Date:** 2026-05-21
**Target release:** v0.5.0
**Builds on:** v0.4.0

## 1. Purpose

Turn Cairn from an app into a *platform* and make it production-grade to operate. Five capabilities: a tokened **public REST API** + outbound **webhooks**, a **templates** gallery (save/instantiate page subtrees & databases), **page version history** (snapshots + restore), an **S3/MinIO file backend** behind the existing `FileStorage` seam, and a **backup/restore CLI**. These are largely additive over v0.1.0–v0.4.0 lib helpers — the API surfaces existing logic; the storage backend fills an interface that already exists.

## 2. Key decisions (made autonomously; revisit before building)

1. **API keys are workspace-scoped, hashed-at-rest, prefixed bearer tokens.** A new `api_keys` table stores a SHA-256 hash of the token (never the plaintext; shown once on creation). Token format `cairn_sk_<32 hex>`; the request sends `Authorization: Bearer cairn_sk_...`. A key carries a `role` (reuses `owner>admin>editor>viewer`) and an optional `expires_at`. API requests resolve to an `AuthContext` exactly like a session does — so the existing `requireRole`/`requirePageAccess` helpers work unchanged. Rationale: one authorization model, no parallel permission code. Keys are managed in workspace settings; revocation = delete row.
2. **The public API is a thin `/api/v1/*` layer over existing lib helpers, versioned by URL.** It exposes read/write for pages, databases, and rows — *not* a new ORM. Each route authenticates the bearer token → `AuthContext`, then calls the same `src/lib/...` functions the session UI uses. Pagination is cursor-based (`?cursor=&limit=`, max 100). Rate limiting is a simple in-process token bucket per key (homelab scale; documented ceiling — not Redis-backed). JSON only. Errors use a consistent `{ error: { code, message } }` shape.
3. **Webhooks are fire-and-forget HTTP POSTs with HMAC signatures and bounded retries.** A `webhooks` table holds `{ workspaceId, url, events[], secret, active }`. Events: `page.created|updated|deleted`, `row.created|updated|deleted`. On a triggering mutation, enqueue a delivery; a small in-process dispatcher POSTs the event JSON with an `X-Cairn-Signature` HMAC-SHA256 header (signed with the per-hook secret), retrying with backoff up to 3 times, recording the last status in a `webhook_deliveries` table. Rationale: no external queue (stays single-process for homelab); at-least-once with visible delivery log. Synchronous mutation latency is unaffected (dispatch is deferred via `setImmediate`/a tiny in-memory queue, not awaited in the request path).
4. **Templates are stored as self-contained JSON snapshots, instantiated with fresh ids.** A `templates` table stores `{ workspaceId, name, kind: 'page'|'database', payload jsonb, builtIn bool }`. Saving a page captures the page subtree (content + descendants) as portable JSON; saving a database captures its properties + views (NOT its rows, unless explicitly "with sample rows"). Instantiating walks the payload, mints new uuids, rewrites internal id references (parent links, relation/rollup property ids, database-node `databaseId`s), and inserts into the target workspace. A handful of **built-in** templates (meeting notes, project tracker DB, weekly planner) ship seeded. Rationale: reuses the export/JSON-walker machinery from v0.1.0; id-rewriting is the only real complexity.
5. **Version history snapshots `pages.content` on a debounce + on explicit save, capped per page.** A new `page_versions` table stores `{ pageId, content jsonb, authorId, createdAt }`. The existing autosave path (or, for collab pages, the materialize-to-`content` step from v0.3.0) writes a version row when content settled and differs from the latest version, debounced (≥ ~60s apart) to avoid keystroke spam. Retention: keep the most recent N (e.g. 50) per page, prune older (a daily/lazy cleanup). A history panel lists versions; "restore" writes the chosen content back as a new current version (non-destructive — restore is itself a new version). Diffs are computed client-side from the two JSON docs (no stored diffs). Rationale: snapshots are simple and robust; diffs are a view concern.
6. **S3/MinIO backend implements the existing `FileStorage` interface; backend is env-selected.** Add `S3Storage` in `src/lib/files/storage.ts` (or a sibling) implementing the same `put/get/delete/exists` contract as the local-disk impl. `FILE_BACKEND=local|s3` selects it at startup; S3 config via `S3_ENDPOINT/S3_BUCKET/S3_ACCESS_KEY/S3_SECRET_KEY/S3_REGION` (MinIO = S3-compatible endpoint). Signed-URL reads still go through `/api/files/[id]?sig=&exp=` (the app streams from the backend); we do NOT switch to S3 presigned URLs in v0.5.0 (keeps the HMAC URL scheme + access checks unchanged). Rationale: the seam is already there; this is a class + a factory switch. **Low risk.**
7. **Backup/restore is a CLI subcommand of the existing entrypoint, operating on Postgres + the uploads volume.** `node dist/cli.js backup --out <dir>` runs `pg_dump` (custom format) of the database and tars the uploads tree (local backend) into a timestamped bundle; `restore --in <bundle>` reverses it (drops/recreates via `pg_restore`, untars uploads), guarded by an interactive confirm + a `--force` flag. For the S3 backend, uploads live in the bucket (backup notes that S3 buckets are backed up out-of-band; the CLI backs up the DB and, for local, the files). Ships documented in the README ops section. Rationale: pragmatic homelab DR; no new infra.

## 3. Scope

### In scope
- `api_keys` table + key mint/hash/verify + `/api/v1` resolution to `AuthContext`; `/api/v1` routes for pages, databases, rows (CRUD, cursor pagination, rate limiting); API-key management UI in workspace settings.
- `webhooks` + `webhook_deliveries` tables; HMAC-signed delivery dispatcher with retries + delivery log; webhook management UI; mutation hooks emitting events.
- `templates` table; save-as-template (page subtree / database) + instantiate-with-fresh-ids; built-in seeded templates; templates gallery UI.
- `page_versions` table; debounced snapshotting wired into the save/materialize path; history panel + restore; retention pruning.
- `S3Storage` implementing `FileStorage`; `FILE_BACKEND` env switch; config plumbing; docker-compose optional MinIO profile for local testing.
- Backup/restore CLI subcommands (`backup`, `restore`) on the entrypoint binary; README ops docs.
- Migration `0012` (api_keys, webhooks, webhook_deliveries, templates, page_versions).

### Deferred
- Redis-backed rate limiting / multi-instance webhook delivery → documented ceiling; in-process for homelab.
- GraphQL or a generated OpenAPI client → REST + a hand-written OpenAPI doc only (stretch within the API plan).
- Per-field/granular API scopes beyond the existing role tiers → role-scoped keys only.
- S3 presigned direct-to-client URLs / multipart upload → app-proxied streaming reuses the existing signed-URL scheme.
- Stored/server-side version diffs, branching history → client-side diff of two snapshots; linear history only.
- Automated off-host backup scheduling/rotation → the CLI is manual/cron-able; no built-in scheduler.
- Template marketplace / sharing across instances → workspace-local + seeded built-ins only.

## 4. Data model (migration `0012`)

```
api_keys
  id            uuid pk
  workspace_id  uuid not null references workspaces(id) on delete cascade
  name          text not null
  token_hash    text not null unique          -- sha256(token); plaintext shown once
  token_prefix  text not null                 -- e.g. 'cairn_sk_ab12' for display/identification
  role          text not null                 -- owner|admin|editor|viewer
  created_by    uuid not null references users(id) on delete restrict
  last_used_at  timestamptz null
  expires_at    timestamptz null
  created_at    timestamptz not null default now()

webhooks
  id            uuid pk
  workspace_id  uuid not null references workspaces(id) on delete cascade
  url           text not null
  events        text[] not null               -- subset of the event names
  secret        text not null                 -- per-hook HMAC secret
  active        boolean not null default true
  created_at    timestamptz not null default now()

webhook_deliveries
  id            uuid pk
  webhook_id    uuid not null references webhooks(id) on delete cascade
  event         text not null
  payload       jsonb not null
  status        text not null                 -- 'pending'|'success'|'failed'
  attempts      integer not null default 0
  last_status   integer null                  -- last HTTP status code
  created_at    timestamptz not null default now()
  delivered_at  timestamptz null

templates
  id            uuid pk
  workspace_id  uuid null references workspaces(id) on delete cascade  -- null = built-in/global
  name          text not null
  kind          text not null                 -- 'page'|'database'
  payload       jsonb not null                -- portable snapshot
  built_in      boolean not null default false
  created_at    timestamptz not null default now()

page_versions
  id            uuid pk
  page_id       uuid not null references pages(id) on delete cascade
  content       jsonb not null                -- ProseMirror JSON snapshot
  author_id     uuid null references users(id) on delete set null
  created_at    timestamptz not null default now()
```

Indexes: `api_keys(token_hash)`, `webhook_deliveries(webhook_id, created_at)`, `page_versions(page_id, created_at desc)`, `templates(workspace_id, kind)`.

## 5. Architecture by area

- **API auth:** `src/lib/api/keys.ts` — `mintKey` (generate token, store hash+prefix, return plaintext once), `verifyKey(token) → AuthContext | null` (hash, lookup, check `expires_at`, set `last_used_at`). `src/lib/api/auth.ts#requireApiAuth(req)` extracts the bearer token, verifies it, returns the same `AuthContext` shape session routes use, so `requireRole`/`requirePageAccess` are reused verbatim. Cross-workspace ids still 404.
- **`/api/v1` routes:** `src/app/api/v1/{pages,databases,rows}/...` — thin handlers calling existing `src/lib` helpers. Shared `withApiKey(handler)` wrapper does auth + rate-limit (token bucket in `src/lib/api/rate-limit.ts`, in-memory `Map<keyId, bucket>`) + uniform error shaping. Cursor pagination helper in `src/lib/api/pagination.ts`.
- **Webhooks:** `src/lib/webhooks/dispatch.ts` — `emit(event, workspaceId, payload)` finds active hooks subscribed to the event, inserts `webhook_deliveries` rows, and schedules delivery (`setImmediate`) without blocking the caller. `deliver(deliveryId)` POSTs with `X-Cairn-Signature: sha256=<hmac>`, retries (3×, exponential backoff), updates status. Mutation sites (page/row create/update/delete in the existing lib helpers) call `emit(...)` after a successful write. A delivery-log view in webhook settings.
- **Templates:** `src/lib/templates/capture.ts` (page subtree → portable JSON; database → properties+views JSON) and `instantiate.ts` (walk payload, mint uuids, rewrite internal references incl. relation/rollup property ids and embedded `databaseId`s, insert). `src/lib/templates/builtins.ts` seeds a few global templates at startup (idempotent upsert by name+built_in). Gallery UI under `src/app/(app)/templates/` + a "Save as template" action on pages/databases.
- **Version history:** `src/lib/pages/versions.ts` — `snapshotIfChanged(pageId, content, authorId)` (compare to latest, debounce by timestamp, insert, prune beyond N) called from the autosave save path and the v0.3.0 collab materialize step; `listVersions`, `restoreVersion` (writes chosen content as current + a new version row). History panel `src/components/pages/version-history.tsx` with client-side JSON diff rendering.
- **S3 storage:** `S3Storage` (AWS SDK v3 `@aws-sdk/client-s3`, MinIO-compatible via custom endpoint + `forcePathStyle`) implementing the `FileStorage` interface; `getStorage()` factory reads `FILE_BACKEND`. No change to `/api/files/[id]` signed-URL handler (it calls `getStorage().get(...)`). docker-compose gains an optional `minio` service under a compose profile for local/dev.
- **Backup CLI:** `src/server/cli.ts` (compiled alongside the entrypoint) with `backup`/`restore` subcommands shelling out to `pg_dump`/`pg_restore` (present in the postgres-client image layer; document the dependency) and `tar` for the uploads dir. Confirmation prompt + `--force`. README "Operations" section documents usage and the S3 caveat.

## 6. Security

- API tokens are never stored or logged in plaintext — only the SHA-256 hash + a short display prefix. Plaintext is returned once at creation. Verification is constant-time on the hash lookup.
- API requests are rate-limited per key; expired/revoked keys are rejected before any business logic. All `/api/v1` access flows through the same role/workspace checks as the UI — no broader reach than a session of the same role.
- Webhook payloads are signed with a per-hook secret (HMAC-SHA256); receivers verify `X-Cairn-Signature`. Webhook URLs are workspace-admin-configured; outbound requests should guard against SSRF to internal addresses (block link-local/loopback/private ranges unless explicitly allowed) — flag for the plan.
- Templates capture content the saver can already read; instantiation inserts only into workspaces the user has editor+ access to. Built-in templates carry no workspace data.
- Version history is workspace-scoped exactly like pages; restore requires editor access. The public render path never exposes versions, API keys, or webhooks.
- Backup bundles contain the full database (including password hashes and API-key hashes) and all files — documented as sensitive; the CLI does not transmit them anywhere.

## 7. Plan decomposition (~5 plans)

1. **Public API + keys** — migration `0012` (api_keys + the other four tables, so later plans depend on it), key mint/hash/verify, `requireApiAuth`, `/api/v1` pages/databases/rows CRUD with cursor pagination + in-process rate limiting, API-key management UI. Includes a hand-written OpenAPI/README API reference (stretch).
2. **Webhooks** — `webhooks`/`webhook_deliveries` already in `0012`; HMAC-signed dispatcher with retries + SSRF guard, `emit(...)` calls wired into page/row mutation helpers, delivery log + webhook management UI.
3. **Templates** — `templates` table already in `0012`; capture (page subtree + database), instantiate-with-fresh-ids (reference rewriting), built-in seeding, gallery + save-as-template UI.
4. **Version history + S3 backend** — `page_versions` already in `0012`; debounced snapshotting wired into save/materialize, history panel + restore + retention pruning; `S3Storage` implementing `FileStorage`, `FILE_BACKEND` switch, MinIO compose profile.
5. **Backup CLI + release** — `backup`/`restore` CLI subcommands, README "Operations" docs, cross-feature smoke (mint a key → API-create a page → fires a webhook → snapshot a version → save a template), CHANGELOG, version bump `0.5.0`, human-run `v0.5.0` tag.

## 8. Risks
- **Webhook dispatch in-process** means deliveries are lost if the process restarts mid-retry; the `webhook_deliveries` rows make this visible and a startup sweep can re-attempt `pending` rows — note in the plan. Document the single-instance ceiling (no distributed queue).
- **Template id-rewriting** must rewrite *every* internal reference: parent links, `databaseId`s embedded in page content nodes, and relation/rollup property-id references inside captured databases — a missed reference yields dangling links in the instantiated copy. Exhaustively unit-test the rewriter against a payload containing all node/property types.
- **Version snapshot volume** could grow large for hot pages; the debounce + per-page cap bound it, but verify pruning runs and that restore is non-destructive.
- **S3 backend** behavioral differences (eventual consistency, missing `exists` semantics) — test against MinIO in CI via Testcontainers; keep the interface contract identical to local.
- **Backup CLI** depends on `pg_dump`/`pg_restore` matching the server major version; pin/document the postgres-client version in the image. `restore` is destructive — gate behind explicit confirmation + `--force`, never run implicitly.
- Rate limiting and SSRF guards are security-load-bearing; do not ship the API/webhooks without them.
