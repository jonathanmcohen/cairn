# Cairn v0.6.0 Plan 9 — Suggestion / Track-Changes Mode

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a Yjs-native suggestion / track-changes mode to the page editor. Proposed edits live **in the same `Y.Doc` as ordinary content** — three marks/node carry author + suggestion id (`suggestion-insert`, `suggestion-delete`, `suggestion-block`) and sync live like any content (the v0.3.0 collab path). A small `suggestions` index table lists open suggestions for permission/notification **without parsing the doc**; `accept`/`reject` flips the marks inside a Yjs transaction and updates the index in lockstep so the index can never drift from the marks. A toolbar toggle enters suggestion mode; `/p/` + `/s/` public render shows the **clean accepted text** (insert text shown, delete text dropped, never the suggestion chrome). Role-gated: `editor`+ proposes and accepts/rejects; `viewer` cannot.

**Architecture:** Three TipTap 3 marks/nodes in `src/components/editor/marks/` (`suggestion-insert.ts`, `suggestion-delete.ts`) + `src/components/editor/suggestion-block.ts`, each carrying `{ suggestionId, authorId, createdAt }` in attrs and registered into both `baseExtensions()` (live editing) and `publicExtensions()` (read-only public render, where they collapse to clean text). A `SuggestionContext` + a toolbar toggle (`src/components/editor/suggestion-toolbar.tsx`) puts the editor into "propose" mode: when on, the editor's keymap routes inserts → wrap in `suggestion-insert`, deletes → wrap in `suggestion-delete` (text is kept, struck through, not removed), and block ops → `suggestion-block`. The pure transform logic lives in `src/lib/suggestions/transform.ts` (apply/accept/reject on a ProseMirror doc, deterministic, unit-tested). `src/lib/suggestions/index-sync.ts` keeps the `suggestions` table consistent: `proposeSuggestion` inserts an `open` row, `acceptSuggestion`/`rejectSuggestion` flip the marks **and** stamp the row in **one** transaction. The collab server already materializes `pages.content` from the merged Yjs doc (v0.3.0 Plan 2); suggestion marks ride that materialization unchanged — only the derived `suggestions` index is a table. The concurrent accept/reject correctness risk (two editors resolving the same suggestion id) is handled by a status-guarded conditional update + a Yjs idempotent mark removal.

**Tech Stack:** TipTap 3 (`@tiptap/core` marks/nodes — no new deps), Yjs / `y-prosemirror` (already present from v0.3.0; suggestion marks ride the existing `Collaboration` binding), Postgres + Drizzle 0.45 (the `suggestions` index + `suggestion_status` enum, migration `0017`), Vitest 4 + Testcontainers v12 (real Postgres) for the index lifecycle + the pure transform logic, Biome 2, pnpm.

**Spec:** `docs/superpowers/specs/2026-05-22-cairn-v0.6.0-design.md` — §2 decision 13 (Yjs-in-doc marks, not a shadow doc; `editor`+ accept/reject), §3 scope (Suggestion mode), §4 migration `0017`, §5 Collaboration → Suggestion mode, §6 testing (suggestion mark accept/reject transforms; `suggestions` lifecycle; Yjs round-trip audit), §8 risk ("Suggestion mode is the hardest collab surface").

**Builds on:** v0.3.0 collab editing (`2026-05-21-cairn-v0.3.0-collab-editing.md`) — assumes committed and live:
- `src/components/editor/extensions.ts` — `baseExtensions({ undoRedo? })` + `collabExtensions(...)` (suggestion marks are added inside `baseExtensions`, so they ride collab automatically).
- `src/components/editor/editor.tsx` — the Yjs-bound `Editor` (no content PATCH; the collab server materializes `pages.content`).
- The `cairn-collab` Hocuspocus service materializing the merged Yjs doc back to `pages.content` (debounced + disconnect-flush) so search/export/public-render keep reading `pages.content`.
- `publicExtensions()` — the read-only render extension set used by `/p/` + `/s/` (this plan adds the three read-only suggestion variants there).
- `src/lib/pages/access.ts#requirePageAccess(pageId, role)` + `src/lib/auth/require-role.ts#hasMinRole` for role gating.

> **SCOPE (strict):** insert / delete / block proposals + accept / reject ONLY. **NO comment-on-suggestion threading** (the comment store is P8; suggestions are not commentable in this release). NO suggestion analytics, NO per-suggestion notification digests beyond the existing notification create path, NO "suggest a property change" on database rows (content marks only).

## Task 1: Migration `0017` — `suggestions` index table + `suggestion_status` enum

**Goal:** A small index table that lists open suggestions per page for permission/notification/listing **without parsing the Yjs doc**. The doc marks are the source of truth for *what* the suggestion is; this table is the source of truth for *status* + ownership.

**Files:** Create `src/db/schema/suggestions.ts`; generate + hand-finish `drizzle/migrations/0017_suggestions.sql`.

- [ ] **Step 1: Write the Drizzle schema `src/db/schema/suggestions.ts`**

`suggestion_status` is a NEW enum → `CREATE TYPE` is **transactional** (unlike `0013`'s `ALTER TYPE ADD VALUE`; see spec §4 + §8). The table cascades on page delete.

```ts
import { sql } from 'drizzle-orm';
import { index, pgEnum, pgTable, timestamp, uuid } from 'drizzle-orm/pg-core';
import { pages } from './pages';
import { users } from './users';

export const suggestionStatus = pgEnum('suggestion_status', ['open', 'accepted', 'rejected']);

export const suggestions = pgTable(
  'suggestions',
  {
    id: uuid('id').primaryKey().defaultRandom(),
    pageId: uuid('page_id')
      .notNull()
      .references(() => pages.id, { onDelete: 'cascade' }),
    authorId: uuid('author_id')
      .notNull()
      .references(() => users.id),
    status: suggestionStatus('status').notNull().default('open'),
    createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
    resolvedAt: timestamp('resolved_at', { withTimezone: true }),
    resolvedBy: uuid('resolved_by').references(() => users.id),
  },
  (t) => [index('suggestions_page_status_idx').on(t.pageId, t.status)],
);
```

## Task 3: Pure accept/reject transform (`transform.ts`) — TDD

**Goal:** A pure module that, given a ProseMirror doc JSON and a `suggestionId`, produces the doc with that suggestion **accepted** or **rejected**, plus a `previewAccepted(doc)` that resolves ALL open suggestions to clean text (used by public render). No Yjs, no DB — deterministic, fully unit-tested. This is the correctness core: the same logic is applied inside a Yjs transaction in Task 4, but the *decision* of what each operation does to the doc lives here and is exhaustively tested.

**Semantics (the contract):**
- **accept insert** → remove the `suggestionInsert` mark, keep the text. **reject insert** → delete the marked text.
- **accept delete** → delete the `suggestionDelete`-marked text. **reject delete** → remove the mark, keep the text.
- **accept suggestionBlock** `kind=insert` → unwrap (lift children out), keep content. `kind=delete` → remove the block. **reject** inverts.
- **previewAccepted(doc)** → apply "accept" to every suggestion mark/node id present (clean accepted text for `/p/` + `/s/`).

```ts
import { getSchema } from '@tiptap/core';
import { type Node as PMNode, Slice } from '@tiptap/pm/model';
import { ReplaceStep, Transform, liftTarget } from '@tiptap/pm/transform';
import { baseExtensions } from '@/components/editor/extensions';

const schema = getSchema(baseExtensions());
const INSERT = 'suggestionInsert';
const DELETE = 'suggestionDelete';
const BLOCK = 'suggestionBlock';

type Json = Record<string, unknown>;

function resolve(doc: Json, fn: (tr: Transform, node: PMNode) => void): Json {
  const node = schema.nodeFromJSON(doc);
  const tr = new Transform(node);
  fn(tr, node);
  return tr.doc.toJSON() as Json;
}

// Walk marked ranges for a given suggestionId + mark type; returns [{from,to}] in
// the ORIGINAL doc coords (caller applies edits high→low so positions stay valid).
function markRanges(node: PMNode, markType: string, id: string): { from: number; to: number }[] {
  const ranges: { from: number; to: number }[] = [];
  node.descendants((child, pos) => {
    const m = child.marks.find((mk) => mk.type.name === markType && mk.attrs.suggestionId === id);
    if (m) ranges.push({ from: pos, to: pos + child.nodeSize });
  });
  return ranges;
}

export function acceptSuggestion(doc: Json, id: string): Json {
  return resolve(doc, (tr, node) => {
    // accept insert: remove the mark (keep text), high→low
    for (const r of markRanges(node, INSERT, id).reverse())
      tr.removeMark(r.from, r.to, schema.marks.suggestionInsert);
    // accept delete: delete the marked text, high→low
    for (const r of markRanges(tr.doc, DELETE, id).reverse()) tr.delete(r.from, r.to);
    // suggestionBlock: accept insert -> lift children; accept delete -> remove
    applyBlock(tr, id, 'accept');
  });
}

export function rejectSuggestion(doc: Json, id: string): Json {
  return resolve(doc, (tr, node) => {
    for (const r of markRanges(node, INSERT, id).reverse()) tr.delete(r.from, r.to);
    for (const r of markRanges(tr.doc, DELETE, id).reverse())
      tr.removeMark(r.from, r.to, schema.marks.suggestionDelete);
    applyBlock(tr, id, 'reject');
  });
}

export function previewAccepted(doc: Json): Json {
  const ids = collectIds(doc);
  return ids.reduce<Json>((d, id) => acceptSuggestion(d, id), doc);
}

## Task 4: `index-sync.ts` — propose / accept / reject keep the index ↔ marks consistent (TDD, the concurrency guard)

**Goal:** The lib that the API calls. `proposeSuggestion(tx, {pageId, authorId})` inserts an `open` row and returns the new `suggestionId` (the client then writes marks carrying that id into the live Yjs doc — the server is NOT the mark writer; see the design note below). `acceptSuggestion`/`rejectSuggestion(tx, {pageId, suggestionId, resolverId})` **(a)** flips the `suggestions` row status from `open`→`accepted`/`rejected` with a **status-guarded conditional update** (so two concurrent resolvers can't both "win"), and **(b)** materializes the resolved doc into `pages.content` by running the Task-3 transform over the current `pages.content` — so the index never drifts from the persisted content. The Yjs marks are removed by the **resolving client** inside a Yjs transaction (idempotent: removing an already-removed mark is a no-op); the server's `pages.content` update is the durable backstop the collab materializer reconciles to.

> **Design note (record in the report) — who edits the Yjs doc on accept/reject, and why it's drift-free:** The marks live in the Yjs doc; the server can't transactionally mutate a live `Y.Doc` it doesn't host (the collab service does). So the contract is: **the resolving client applies the Task-3 transform to the live Yjs doc inside one `ydoc.transact()`** (idempotent mark removal), AND the API call flips the index row + writes the transformed `pages.content` (the same transform, server-side, over the last-materialized content). Both sides use the **same pure `transform.ts`**, so they converge. If a client is offline when another accepts, the collab materializer's next flush re-derives `pages.content` from the merged doc — and because mark removal is idempotent and the index row is already `accepted`, re-resolution is a no-op. The status-guarded `WHERE status = 'open'` update is the single point that decides the winner under a concurrent accept/reject race.

import { and, eq, sql } from 'drizzle-orm';
import type { Db } from '@/db/client'; // confirm the exported db/tx type name
import { suggestions } from '@/db/schema/suggestions';
import { pages } from '@/db/schema/pages';
import { acceptSuggestion as acceptDoc, rejectSuggestion as rejectDoc } from './transform';

export async function proposeSuggestion(db: Db, args: { pageId: string; authorId: string }): Promise<string> {
  const [row] = await db.insert(suggestions)
    .values({ pageId: args.pageId, authorId: args.authorId, status: 'open' })
    .returning({ id: suggestions.id });
  return row.id;
}

export async function listOpenSuggestions(db: Db, pageId: string) {
  return db.select().from(suggestions)
    .where(and(eq(suggestions.pageId, pageId), eq(suggestions.status, 'open')));
}

type ResolveArgs = { pageId: string; suggestionId: string; resolverId: string };
type ResolveResult = { resolved: boolean };

async function resolve(db: Db, args: ResolveArgs, status: 'accepted' | 'rejected',
  transformDoc: (doc: Record<string, unknown>, id: string) => Record<string, unknown>): Promise<ResolveResult> {
  return db.transaction(async (tx) => {
    // Status-guarded conditional flip: ONLY an `open` row can be resolved. This is
    // the single point that decides the winner under a concurrent accept/reject race.
    const flipped = await tx.update(suggestions)
      .set({ status, resolvedBy: args.resolverId, resolvedAt: sql`now()` })
      .where(and(eq(suggestions.id, args.suggestionId), eq(suggestions.status, 'open')))
      .returning({ id: suggestions.id });
    if (flipped.length === 0) return { resolved: false }; // already resolved — no-op

    // Materialize the resolved doc into pages.content (same pure transform the
    // resolving CLIENT applies to the live Y.Doc; idempotent + convergent).
    const [page] = await tx.select({ content: pages.content }).from(pages).where(eq(pages.id, args.pageId));
    const next = transformDoc(page.content as Record<string, unknown>, args.suggestionId);
    await tx.update(pages).set({ content: next, updatedAt: sql`now()` }).where(eq(pages.id, args.pageId));
    return { resolved: true };
  });
}

export const acceptSuggestion = (db: Db, args: ResolveArgs) => resolve(db, args, 'accepted', acceptDoc);
export const rejectSuggestion = (db: Db, args: ResolveArgs) => resolve(db, args, 'rejected', rejectDoc);
```

  const { ctx } = await requirePageAccess(pageId, 'editor');
  const { action } = Body.parse(await req.json());
  const fn = action === 'accept' ? acceptSuggestion : rejectSuggestion;
  const { resolved } = await fn(getDb(), { pageId, suggestionId, resolverId: ctx.userId });
  if (!resolved) return NextResponse.json({ error: 'already_resolved' }, { status: 409 });
  return NextResponse.json({ ok: true });
}
