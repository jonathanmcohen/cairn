- [ ] **Step 3: Establish the curl signup + CSRF-credentials-login helpers**

Reuse the signup + CSRF-credentials-login pattern from the prior plans' smokes. Auth.js credentials login is a CSRF-protected form POST to `/api/auth/callback/credentials`; you must fetch a CSRF token first and carry the cookie jar. Two separate cookie jars are needed because the invite-accept test (Step 6) requires a **second logged-in account**.

```sh
BASE=http://localhost:3000
JAR_A=/tmp/cairn_a.cookies      # first user (workspace owner)
JAR_B=/tmp/cairn_b.cookies      # second user (invited member)
rm -f "$JAR_A" "$JAR_B"

# Sign up user A (first user → becomes owner of a bootstrap workspace "WS-A").
curl -s -c "$JAR_A" -b "$JAR_A" -X POST "$BASE/api/auth/signup" \
  -H 'content-type: application/json' \
  -d '{"email":"a@example.com","password":"password-aaaaaa","name":"User A","workspaceName":"WS-A"}'; echo

# Helper: log in via the credentials provider (CSRF token + cookie jar).
login() {  # $1=jar $2=email $3=password
  local jar="$1" email="$2" pass="$3"
  local csrf
  csrf=$(curl -s -c "$jar" -b "$jar" "$BASE/api/auth/csrf" | sed -E 's/.*"csrfToken":"([^"]+)".*/\1/')
  curl -s -c "$jar" -b "$jar" -o /dev/null -w '%{http_code}\n' \
    -X POST "$BASE/api/auth/callback/credentials" \
    -H 'content-type: application/x-www-form-urlencoded' \
    --data-urlencode "csrfToken=$csrf" \
    --data-urlencode "email=$email" \
    --data-urlencode "password=$pass" \
    --data-urlencode "callbackUrl=$BASE/"
}

login "$JAR_A" a@example.com password-aaaaaa
# Confirm the session resolves:
echo "A session:"; curl -s -b "$JAR_A" "$BASE/api/auth/session"; echo
```

NOTE on field names: the exact signup body keys (`workspaceName`, etc.) and the invite endpoints must match what Plans 1–2 actually shipped. If a request 400s, read the route handler under `src/app/api/...` to confirm the field names rather than guessing — adjust the curl payloads to match.

- [ ] **Step 4: (b) Create a second workspace, switch, verify getAuthContext scoping**

A page created in workspace B must NOT be visible from workspace A (cross-workspace isolation flows through `getAuthContext` active-workspace resolution).

```sh
# Create WS-B (caller A becomes its owner; the new ws is set active via cookie).
WSB=$(curl -s -b "$JAR_A" -c "$JAR_A" -X POST "$BASE/api/workspaces" \
  -H 'content-type: application/json' -d '{"name":"WS-B"}')
echo "create WS-B: $WSB"
WSB_ID=$(echo "$WSB" | sed -E 's/.*"id":"([^"]+)".*/\1/')

# Active workspace is now WS-B (the create switched it). Create a page in WS-B.
PAGE_B=$(curl -s -b "$JAR_A" -c "$JAR_A" -X POST "$BASE/api/pages" \
  -H 'content-type: application/json' -d '{"title":"Secret in B"}')
echo "page in B: $PAGE_B"
PAGE_B_ID=$(echo "$PAGE_B" | sed -E 's/.*"id":"([^"]+)".*/\1/')

# Switch back to WS-A. (Capture WS-A's id from the session/memberships first if the
# switch endpoint needs it; the switch validates membership.)
WSA_ID=$(curl -s -b "$JAR_A" "$BASE/api/workspaces" | sed -E 's/.*"id":"([^"]+)".*/\1/')
curl -s -b "$JAR_A" -c "$JAR_A" -X POST "$BASE/api/workspaces/switch" \
  -H 'content-type: application/json' -d "{\"workspaceId\":\"$WSA_ID\"}" -o /dev/null -w 'switch→A: %{http_code}\n'

# From WS-A, the WS-B page must be 404 (cross-workspace returns 404, not 403).
curl -s -b "$JAR_A" -o /dev/null -w 'A reads B page (expect 404): %{http_code}\n' \
  "$BASE/api/pages/$PAGE_B_ID"
```

Expected: `switch→A: 200`, and reading the WS-B page from the WS-A active context returns `404`.

- [ ] **Step 5: (c) Issue an invite, accept it as an existing logged-in second user**

Sign up user B as their own account first, log them in (jar B), then have owner A (active in WS-A) issue an invite for B's email, and have B accept it via `POST /api/invites/accept`. Confirm B's membership and that B's active workspace switched to WS-A.

```sh
# Sign up user B as a standalone account (their own bootstrap workspace).
curl -s -c "$JAR_B" -b "$JAR_B" -X POST "$BASE/api/auth/signup" \
  -H 'content-type: application/json' \
  -d '{"email":"b@example.com","password":"password-bbbbbb","name":"User B","workspaceName":"WS-B-own"}'; echo
login "$JAR_B" b@example.com password-bbbbbb

# Owner A (active in WS-A) issues an invite for b@example.com as an editor.
INVITE=$(curl -s -b "$JAR_A" -X POST "$BASE/api/invites" \
  -H 'content-type: application/json' -d '{"email":"b@example.com","role":"editor"}')
echo "invite: $INVITE"
TOKEN=$(echo "$INVITE" | sed -E 's/.*"token":"([^"]+)".*/\1/')

# B accepts the invite (existing logged-in user path). Email must match B's verified email.
curl -s -b "$JAR_B" -c "$JAR_B" -X POST "$BASE/api/invites/accept" \
  -H 'content-type: application/json' -d "{\"token\":\"$TOKEN\"}" \
  -o /dev/null -w 'B accept invite: %{http_code}\n'

# B's memberships now include WS-A; active workspace switched to WS-A.
echo "B session after accept (expect WS-A active):"
curl -s -b "$JAR_B" "$BASE/api/auth/session"; echo
```

Expected: `B accept invite: 200`; B now belongs to WS-A with role `editor`, and B's active workspace is WS-A.

- [ ] **Step 6: (d) Leave a workspace + sole-owner rejection**

B (a non-sole-owner member of WS-A) can leave. A, as the **sole owner** of WS-A, must be rejected.

```sh
# B leaves WS-A (must be active in WS-A or pass the id, per the leave route's contract).
curl -s -b "$JAR_B" -c "$JAR_B" -X POST "$BASE/api/workspaces/$WSA_ID/leave" \
  -o /dev/null -w 'B leave WS-A (expect 200): %{http_code}\n'

# A is the sole owner of WS-A → leave must be rejected (no transfer/delete in 0.2.0).
curl -s -b "$JAR_A" -c "$JAR_A" -X POST "$BASE/api/workspaces/$WSA_ID/leave" \
  -o /dev/null -w 'A (sole owner) leave WS-A (expect 4xx): %{http_code}\n'
```

Expected: B's leave → `200`; A's leave → a 4xx rejection (e.g. `409`/`400`/`403` — confirm the exact code against the leave route's contract).

- [ ] **Step 7: (e) Publish → anonymous `/p/<slug>` (image + read-only DB) → unpublish → 404**

Build a page in WS-A with an embedded image (valid signed URL re-minted at public-render time) and an inline database, publish it, fetch `/p/<slug>` with **no cookie**, then unpublish and confirm the slug 404s.

```sh
# Re-confirm A is active in WS-A.
curl -s -b "$JAR_A" -c "$JAR_A" -X POST "$BASE/api/workspaces/switch" \
  -H 'content-type: application/json' -d "{\"workspaceId\":\"$WSA_ID\"}" -o /dev/null -w 'A→WS-A: %{http_code}\n'

# Create a page to publish. (Embed an uploaded image + an inline database in its content —
# do this via the upload + database APIs and a page-content update, mirroring the v0.1.0
# files/databases smoke. Capture the page id.)
PAGE_PUB=$(curl -s -b "$JAR_A" -X POST "$BASE/api/pages" \
  -H 'content-type: application/json' -d '{"title":"Public Roadmap"}')
PAGE_PUB_ID=$(echo "$PAGE_PUB" | sed -E 's/.*"id":"([^"]+)".*/\1/')
echo "page to publish: $PAGE_PUB_ID"

# (Upload an image → get fileId; create an inline database on the page → get databaseId;
#  PATCH the page content jsonb to embed a cairnImage node referencing the fileId and a
#  database node referencing the databaseId. See the Plan 4/5 v0.1.0 smoke for the exact
#  content shape.)

# Publish.
PUB=$(curl -s -b "$JAR_A" -X POST "$BASE/api/pages/$PAGE_PUB_ID/publish")
echo "publish: $PUB"
SLUG=$(echo "$PUB" | sed -E 's/.*"slug":"([^"]+)".*/\1/')   # adjust key if the route returns publicSlug/url
echo "slug: $SLUG"

# Anonymous fetch (NO cookie) of the public render — expect 200.
curl -s -o /dev/null -w '/p/<slug> anon (expect 200): %{http_code}\n' "$BASE/p/$SLUG"

# Confirm the public page emits noindex (unlisted).
curl -s "$BASE/p/$SLUG" | grep -i 'name="robots"' && echo "noindex present"

# The embedded image must be reachable anonymously via its re-minted signed URL.
IMG=$(curl -s "$BASE/p/$SLUG" | grep -oE '/api/files/[^"?]+\?sig=[^"&]+&exp=[0-9]+' | head -1)
echo "signed image url: $IMG"
curl -s -o /dev/null -w 'anon image (expect 200): %{http_code}\n' "$BASE$IMG"

# The read-only embedded database must be reachable anonymously.
DBID=$(curl -s "$BASE/p/$SLUG" | grep -oE 'databases/[0-9a-f-]{36}' | head -1 | sed 's#databases/##')
curl -s -o /dev/null -w 'anon public db read (expect 200): %{http_code}\n' \
  "$BASE/api/public/databases/$DBID"

# Unpublish → /p/<slug> must now 404.
curl -s -b "$JAR_A" -o /dev/null -w 'unpublish: %{http_code}\n' \
  -X POST "$BASE/api/pages/$PAGE_PUB_ID/unpublish"
curl -s -o /dev/null -w '/p/<slug> after unpublish (expect 404): %{http_code}\n' "$BASE/p/$SLUG"
```

Expected: anon `/p/<slug>` → `200` with `noindex`; anon image → `200`; anon `/api/public/databases/<id>` → `200`; after unpublish, `/p/<slug>` → `404`.

NOTE on the embed step: the exact content-jsonb shape for a `cairnImage` / `database` node and the publish-route response key (`slug` vs `publicSlug` vs `url`) come from Plans 1/3. If a `grep` finds nothing, inspect the rendered HTML and the publish route's JSON to fix the extraction.

<PUBLIC_URL>/api/auth/callback/google
<PUBLIC_URL>/api/auth/callback/github

- GitHub: https://github.com/settings/developers

set, Cairn shows only the email/password form — no dead buttons.
