# G10 — Real-time Sidebar + List Refresh Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Every in-app list that mutates via a client action must update without a manual page refresh (F5). The user-reported defect (finding S): clicking the sidebar row `+` (add-child) or `…` → Duplicate navigates to the new page id but the sidebar page-tree keeps showing the stale list until F5. Fix that, then lock the broader audit (favorites, recents, notifications list/drawer, comments list) with regression tests so no list can silently fall back to "stale until refresh".

**Architecture:** The sidebar page-tree is **server-rendered initial props**, not a client query. `SidebarContent` (`src/components/sidebar-content.tsx`) is an `async` server component that calls `flattenedPageTree(getDb(), workspaceId, ctx?.userId)` and passes the result as `<VirtualizedPageTree initial={tree} />` (a `'use client'` component that holds `initial` as its render source). There is no SWR/store/event-bus feeding the tree — so the correct, lightest invalidation is **`router.refresh()`**: it re-runs the server component tree (re-fetching `flattenedPageTree`) and reconciles the client without a full reload. This is the mechanism the codebase **already** uses for tree mutations — `NewPageButton.onClick` does `router.push(...)` **then** `router.refresh()`; `usePageRowActions.moveToTrash` and `submitRename` already call `router.refresh()`; the Move-To picker's `onMoved` callback calls `router.refresh()`. The defect is a **consistency gap**: in `src/components/sidebar/use-page-row-actions.tsx` the `addChild` and `duplicate` callbacks call `router.push(\`/pages/${id}\`)` **without** a following `router.refresh()`, so the new node is never reconciled into the still-mounted sidebar. The fix is to standardize: **every successful mutating fetch in `usePageRowActions` is followed by `router.refresh()`** (navigation-then-refresh for create/duplicate; refresh-only for trash/rename, already present).

The other lists in the audit are already correct and use the *appropriate* mechanism for their data flow — this plan does NOT change their mechanism, it adds a regression test that pins the behavior:
- **Favorites** (`src/components/sidebar-favorites.tsx`): server-fed `initial` + optimistic local `setItems` on remove, then `router.refresh()`. Correct.
- **Recents** (`src/components/sidebar-recents.tsx`): purely presentational, server-fed, no in-component mutation (the recents list is recomputed server-side on navigation). No action needed; covered by the sidebar `router.refresh()` path.
- **Notifications drawer** (`src/components/notifications/drawer.tsx`): client `useSWR` + `mutate()` after mark-read / mark-all-read. Correct.
- **Notifications page list** (`src/components/notifications/page-list.tsx`): server `initial` + optimistic local `setItems` on mark-read. Correct.
- **Comments panel** (`src/components/comments/comment-panel.tsx`): client `refetch()` on open + optimistic local `setComments` on add/resolve/delete. Correct.

So this plan is intentionally small: ONE production code change (Task 1) plus regression-pinning tests (Tasks 1–3). No new dependency, no event bus, no shared store — `router.refresh()` is the cleanest cross-cutting answer because the only stale list is the one whose data is server-component-owned and whose mutations skipped the refresh.

**Tech Stack:** Next.js 16 / React 19 / TS6 strict, `next/navigation` `useRouter().refresh()`, `next/link` typed routes (`as Route`), Vitest 4 (jsdom for components) + `@testing-library/react` (`renderHook`, `render`), Biome v2, i18n flat-dot-key catalogs in `messages/{en,es,ar}.json` via `useT()`. No DB/migration; no Testcontainers (all touched tests are jsdom component/hook tests).

**Closes:** finding S (real-time sidebar + list refresh)

## Background — the real cause (read before Task 1)

Confirmed by reading the source (do NOT re-guess):

- `src/components/sidebar-content.tsx` is an `async` **server** component. It computes `const tree = await flattenedPageTree(getDb(), workspaceId, ctx?.userId);` and renders `<VirtualizedPageTree initial={tree} />` (line ~57). The tree data therefore comes from a server render, not a client fetch — there is no SWR cache, store, or query keyed on it.
- `src/components/sidebar/virtualized-page-tree.tsx` `VirtualizedPageTree({ initial })` uses `initial` directly (via `useMemo(() => buildRows(initial, spaces), ...)`). It has no refetch of its own. So the only way new server data reaches it is a re-render of the server component → `router.refresh()`.
- `src/components/sidebar/use-page-row-actions.tsx` `usePageRowActions(node)` owns the row mutations:
  - `addChild` (lines ~58–67): `await fetch('/api/pages', { method: 'POST', ... })` → on ok, `router.push(\`/pages/${id}\`)`. **No `router.refresh()`.** ← bug.
  - `duplicate` (lines ~69–75): `await fetch(\`/api/pages/${node.id}/duplicate\`, { method: 'POST' })` → on ok, `router.push(\`/pages/${id}\`)`. **No `router.refresh()`.** ← bug.
  - `moveToTrash` (lines ~77–86): `DELETE /api/pages/${id}` → on ok, `router.refresh()`. Correct (keep).
  - `submitRename` (lines ~88–101): `PATCH /api/pages/${id}` → on ok, `router.refresh()`. Correct (keep).
  - Move-To is opened via `moveTo.run` → the picker is mounted by `page-row-actions-menu.tsx` / `page-row-context-menu.tsx` with `onMoved={() => router.refresh()}`. Correct (keep).
- For comparison, `src/components/new-page-button.tsx` `onClick` already does `router.push(...)` **then** `router.refresh()` — the exact pattern `addChild`/`duplicate` are missing.

**Therefore:** the only production fix is to add `router.refresh()` after the successful `push` in `addChild` and `duplicate`. Everything else in the audit is already correct and only needs a regression test.
